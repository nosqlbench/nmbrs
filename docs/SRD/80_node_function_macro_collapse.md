# SRD-80 — Node Function Macro Collapse (`#[polydat_node]`)

**Status:** SUPERSEDED for the open design questions — see
**[SRD-80b](80b_macro_universal_authoring.md)** for the
committed architectural answer. This SRD remains the
historical scoping doc and PR B.1-B.15 shipping record; new
design work and the next implementation push are governed by
SRD-80b.

The open design questions enumerated in this document are
RESOLVED by SRD-80b's commitments:

- Macro is the **sole** authoring path (no NodeImpl escape).
- Type identity is Rust types + serde_json::Value semantics;
  `PortType` / `SlotType` / `JitType` are macro-internal
  projections derived from the `Wire` trait.
- Variadic / polymorphic / state / Ext / fallible-construction
  shapes all reduce to **one combinator impl + one recognition
  arm** in the macro — see SRD-80b §"The macro contract".
- `NodeRegistration` is the fusion-compiler input; the macro
  reifies everything fusion needs.

PR B.1 through B.15 shipped under this SRD's scoping and stand;
the canonical-form table in SRD-80b §"Authoring patterns" is
the authoritative pattern catalog from PR B.16 onward.

**Owner:** polydat (library, registry, factory registration,
DSL compiler).

## The problem this SRD targets

Every polydat library node today carries multiple
overlapping representations:

1. **The struct** with the `meta: NodeMeta` field.
2. **`Default + new()`** constructor that initializes the
   `NodeMeta` with `name`, `ins` (with `Port::new("name",
   PortType::*)` per input), `outs` (same shape for outputs).
3. **`impl PolydatNode`** with `meta(&self)` + `eval(&self,
   inputs: &[Value], outputs: &mut [Value])` doing manual
   `Value::as_*` unboxing and `Value::*(...)` reboxing per
   call.
4. **Optional `compiled_u64(&self)` / similar** JIT hooks
   shadowing the eval logic in typed-u64 form.
5. **`FuncSig`** in the factory's `signatures()` listing —
   `params: &[ParamSpec]` with `SlotType::Wire(PortType)`
   (after SRD-79 PR A.1) for every input slot.
6. **Factory dispatch** — the factory's `build` method
   matches on `name` and calls the matching `new()`.

Items 1–4 are partly collapsed by the existing declarative
macros (`cmp_u64_node!`, `unary_f64_node!`, `binary_u64_node!`,
`cmp_f64_node!`, `handle_indexed_node!`, etc.). Item 5 is
NOT generated by those macros today — it lives separately
in each factory's `signatures()` method, hand-maintained.
Item 6 dispatch tables are also hand-maintained.

The result: roughly 5 places need to stay in sync per node.
Adding a new node means writing 30–60 lines of metadata
plumbing for what is fundamentally a function:

```rust
// What the node IS, conceptually:
fn str_eq(a: Str, b: Str) -> U64 { if a == b { 1 } else { 0 } }
```

**The vision**: a single proc-macro that takes the function
above and derives everything — struct, NodeMeta, impl
PolydatNode (with boxing/unboxing), FuncSig, factory
registration. The Rust function signature is the source of
truth; the metadata is derived.

## The target surface

```rust
#[polydat_node]
fn str_eq(a: Str, b: Str) -> U64 {
    if a == b { 1 } else { 0 }
}
```

Macro generates (approximately):

```rust
pub struct StrEq { meta: NodeMeta }
impl Default for StrEq { fn default() -> Self { Self::new() } }
impl StrEq {
    pub fn new() -> Self {
        Self {
            meta: NodeMeta {
                name: "str_eq".into(),
                ins: vec![
                    Slot::Wire(Port::new("a", PortType::Str)),
                    Slot::Wire(Port::new("b", PortType::Str)),
                ],
                outs: vec![Port::new("output", PortType::U64)],
            }
        }
    }
}
impl PolydatNode for StrEq {
    fn meta(&self) -> &NodeMeta { &self.meta }
    fn eval(&self, inputs: &[Value], outputs: &mut [Value]) {
        let a = <Str as FromValue>::from_value(&inputs[0]);
        let b = <Str as FromValue>::from_value(&inputs[1]);
        outputs[0] = (str_eq(a, b)).into_value();
    }
}
// FuncSig auto-registered into the polydat function registry
inventory::submit! {
    FuncSig {
        name: "str_eq",
        category: FuncCategory::Comparison,
        outputs: 1,
        params: &[
            ParamSpec { name: "a", slot_type: SlotType::Wire(PortType::Str), ... },
            ParamSpec { name: "b", slot_type: SlotType::Wire(PortType::Str), ... },
        ],
        arity: Arity::Fixed,
        // ...
    }
}
```

(`inventory` is one possible registration mechanism — Rust's
`linkme` or compile-time slice collection are alternatives.
The exact mechanism is one of the open design questions.)

## What needs to be derived

The macro infers everything in items 1–6 from the function
signature plus optional attribute metadata:

- **Function name** → `NodeMeta.name`, `FuncSig.name`. Defaults
  to the Rust function name; override via `#[polydat_node(name
  = "...")]`.
- **Each arg type** → `Slot::Wire(Port::new(arg_name,
  port_type))` + `FuncSig.params` entry with
  `SlotType::Wire(port_type)`.
- **Return type** → `NodeMeta.outs` with the matching
  `PortType`.
- **Function body** → wrapped in the `eval` boxing/unboxing
  bridge using `FromValue` / `IntoValue` trait impls (defined
  for `Str`, `U64`, `F64`, `Bool`, `VecU64`, etc.).
- **`FuncSig` registration** → emitted via `inventory::submit!`
  or equivalent, so factories don't need separate dispatch
  tables.

## Escape hatches (RESOLVED — see SRD-80b)

> **Status — RESOLVED**: SRD-80b commits that **the macro IS
> the only authoring path**. There is no hand-written escape
> hatch. Every shape below becomes one combinator impl + one
> recognition arm in the macro per the SRD-80b canonical-form
> table. The shapes below remain accurate descriptions of the
> need; the resolution is "the macro absorbs them," not "the
> operator gets a different surface."

Not every node fits the "pure function over typed args"
shape. The follow-on session needs to characterize the
escape hatches:

### State-bearing nodes

Some nodes carry per-instance state across cycles
(accumulators, peak trackers, source readers). The `eval`
shape changes from `fn(args) -> Result` to `fn(&mut self,
args) -> Result`. The macro needs an attribute form:

```rust
#[polydat_node(state = AccumulatorState)]
fn running_sum(value: U64) -> U64 {
    // implicit `state: &mut AccumulatorState` parameter
    state.total += value;
    state.total
}
```

### JIT-eligible nodes

Nodes that participate in the JIT (P3) path expose
`compiled_u64`, `jit_constants`, and related hooks. The
existing macros (`cmp_u64_node!`) generate these for the
regular u64-arithmetic shape. The proc-macro needs to:

1. Detect when the eval body is JIT-eligible by analysis (all
   args + return are u64, no side effects, etc.) — or by
   explicit attribute.
2. Generate the matching `compiled_u64` impl.

Initial implementation can require an explicit
`#[polydat_node(jit = true)]` attribute; fully automatic
detection is a follow-up.

### Const constraints

Some const-arg parameters carry assembly-time validation
(`ConstConstraint`). The macro needs to surface a way to
attach these:

```rust
#[polydat_node]
fn regex_match(
    input: Str,
    #[constraint(regex_valid)] pattern: ConstStr,
) -> U64 { ... }
```

### Variadic shapes

`sum`, `concat`, `min`, `max`, and other variadic nodes
take a variable number of inputs. The macro vocabulary
needs to express:

```rust
#[polydat_node(variadic = "wires")]
fn sum(args: Variadic<U64>) -> U64 {
    args.iter().sum()
}
```

The corresponding `Arity::VariadicWires { min_wires }` would
be derivable from the type signature plus an attribute.

### Polymorphic output (`SameAsInput(usize)`)

`identity`, `log_info`, and pass-through nodes have an output
type that matches one of their input types. Express via
generic:

```rust
#[polydat_node]
fn log_info<T: PolydatType>(value: T) -> T {
    eprintln!("{value:?}");
    value
}
```

The macro derives `OutputType::SameAsInput(0)` from the
shared `T` type parameter.

### Adapter-contributed `Ext` types

`Value::Ext(Box<dyn ReflectedValue>)` is the catch-all for
adapter-provided types (CQL UUID, timestamps, etc.). The
macro vocabulary needs a way to declare nodes that consume
or produce specific reflected types — likely via a trait
bound on the arg type.

## Open design questions (RESOLVED — see SRD-80b)

> **Status — RESOLVED**: every question below was answered
> during the focused design session and the answers are
> codified in **[SRD-80b](80b_macro_universal_authoring.md)**.
> They are preserved here as historical context. **Do not
> treat the questions below as open** — SRD-80b is the
> authoritative answer for each.

1. **Procedural macro crate organization.** Standalone
   `polydat-derive` crate? Inline `proc-macro` in
   `polydat-core`? Build-time impact and compile-time cost
   measured against the existing declarative-macro baseline.

2. **Trait surface for the type ↔ Value bridge.** `FromValue` /
   `IntoValue` traits implemented for every primitive
   PortType. What about `Value::Json`? `Value::Handle`?
   `Value::Ext` (with downcast)? Need to specify the trait
   surface that the macro-generated `eval` wrapper expects.

3. **Variadic shape vocabulary.** Pick a representation:
   `Variadic<T>`, slice arg `&[T]`, repeat-attribute
   `#[polydat_node(repeat_from = 0)]`. Decide whether
   `Arity::VariadicWires` / `VariadicConsts` /
   `VariadicGroup` are all needed under the new surface or
   if some collapse.

4. **Polymorphic input (`SameAsInput`).** How to encode the
   "all args share a type" constraint. Generic over a single
   `T`? Trait `PolydatType` covering every primitive? Less
   ambitiously: limit polymorphism to a known list of
   numeric-or-string variants and skip generics.

5. **Registration mechanism.** `inventory` crate (which has
   stable cross-version reliability concerns),
   `linkme` (similar caveats), or compile-time generation of
   a registration function the polydat init code calls? Want
   no-startup-cost lookup.

6. **Co-existence with existing declarative macros.** Strategy
   for migration: convert all at once or per-module? The
   declarative macros do exactly what the proc macro will do
   for the regular cases — the proc macro is more flexible.
   Worth keeping both? Or commit to proc macro and retire
   the declarative macros?

7. **Attribute vocabulary for the escape hatches.** Finalize
   the attribute names — `state`, `jit`, `variadic`,
   `constraint`, `category`, `name`. Document each.

8. **Diagnostic surface.** When the macro can't derive
   metadata (e.g. unknown arg type, missing trait impl),
   what does the error message look like? The macro should
   produce errors that point at the function signature, not
   at the generated code.

## Implementation map (historical — PRs B.1-B.15 shipped here; B.16+ governed by SRD-80b)

> **Status — PARTIAL**: PRs B.1 through B.15 shipped under
> this implementation map and stand. The Wave 2 implementation
> plan (Phases 1-7, including the universal-set refactor and
> the migration of the residual ~111 hand-written nodes) is in
> **[SRD-80b §"Migration plan"](80b_macro_universal_authoring.md#migration-plan)**.

The follow-on session will produce the full SRD with these
sections detailed:

- **PR B.1**: `polydat-derive` crate scaffolding +
  `FromValue` / `IntoValue` trait surface + macro skeleton
  that handles the simplest case (pure function, all
  primitive args, no state, no JIT).
- **PR B.2**: pilot migration — convert ~5 nodes (one from
  each existing declarative-macro family) to the proc-macro
  form. Validate the generated output matches the manual
  version byte-for-byte at the assembly level.
- **PR B.3** through **PR B.N**: per-module migration. Each
  PR converts one library module
  (`polydat/src/library/{compare,convert,string,math,…}.rs`).
- **PR B.final**: retire the declarative macros (or document
  why they stay).

Migration order is determined by complexity: simplest first
(pure-function nodes), state-bearing nodes mid-stream, JIT-
heavy nodes last. SRD-16's JIT contract is the most
constraining — nodes participating in P3 need the proc
macro to emit the same hooks the JIT relies on.

## What this SRD does NOT cover

- **Workload-side authoring**. SRD-80 is about the LIBRARY
  side (how polydat nodes are declared in the polydat crate).
  Workload-author DSL syntax (`polydat`-language source
  files) doesn't change.
- **Macro-internal type-system surface (REVISED by SRD-80b)**.
  SRD-80 originally said "PortType and Value variants stay
  as-is." SRD-80b refines this: `Value` stays a closed enum
  (semantically aligned with `serde_json::Value` plus polydat
  extensions); `PortType` / `SlotType` / `JitType` become
  **macro-internal projections** derived from the `Wire`
  trait. Operator-facing function signatures use Rust types
  directly. This is a macro-internal refactor, not a runtime
  type-system change — SRD-79's work and the runtime contracts
  are unaffected.
- **JIT codegen changes**. SRD-16 governs JIT eligibility
  and codegen. The macro generates the JIT hooks the runtime
  expects; the JIT itself is untouched. SRD-80b §"NodeRegistration"
  expands the metadata fusion can read but does not alter JIT
  semantics.

## When the follow-on session happens

After SRD-79 ships at minimum PR A.1 (the `SlotType::Wire(PortType)`
registry extension). The macro work needs the post-PR-A.1
`FuncSig` shape as its target. Migrating nodes BEFORE PR A.1
would require designing the macro for two `SlotType` shapes
(pre-extension and post-extension), which doubles the work.

  generalize and the special cases that don't.

  the primitive PortTypes; verify it compiles cleanly and
  the type inference works without explicit turbofish.

  cross-version stability concerns and pick a registration
  mechanism.

open design questions above, ready to refine in the session.
